# RestoFlow ERP — دليل التحقق الشامل وقائمة اختبارات UAT

هذا الدليل هو خطة اختبار تشغيلية للتأكد من أن النظام يعمل فعليًا، وليس مجرد أن الصفحات تفتح. كل اختبار يجب أن ينتهي بحالة واضحة:

النسخة التفاعلية للاستخدام أثناء الاختبار: [`uat-manual.html`](../uat-manual.html).

- `[ ]` لم يُختبر
- `[x]` ناجح
- `[F]` فاشل — يجب تسجيل عطل
- `[B]` محظور بسبب البيئة أو نقص بيانات
- `[S]` غير منطبق على الفرع

> مهم: وجود route أو component أو اختبار آلي لا يعني أن الميزة تم قبولها تشغيليًا. لا نضع علامة نجاح إلا بعد تنفيذ الخطوات ومراجعة النتيجة المتوقعة.

## 1. تجهيز بيئة الاختبار

### 1.1 بيانات وبيئة مطلوبة

- [ ] نسخة اختبار منفصلة عن الإنتاج، مع backup قابل للاسترجاع.
- [ ] فرعان تجريبيان على الأقل: `BR-01` و`BR-02`.
- [ ] مستخدم لكل دور: Super Admin، Owner، Branch Manager، Cashier، Waiter/Captain، Kitchen، Call Center، Accountant، HR، Driver، مستخدم بلا صلاحية.
- [ ] صنف مخزني خام، صنف مركب بوصفة، صنف جاهز، صنف له modifiers، وصنف غير متاح.
- [ ] مورد، مخزنان، طاولة، منطقة توصيل، سائق، عميل، موظف، جهاز طباعة، وبيانات حضور.
- [ ] وسائل دفع: نقدي، بطاقة/شبكة، دفع مقسم، ووسيلة فاشلة للتجربة.
- [ ] تاريخ تشغيل مفتوح وتاريخ آخر مغلق، مع فترة تقارير معروفة.
- [ ] نسخة اختبار من إعدادات الضرائب، العملة، اللغة، الإيصال، الفرع، والمخزون.
- [ ] أدوات تسجيل: DevTools Console/Network، رقم الطلب، رقم الفاتورة، وقت التنفيذ، واسم المستخدم.

### 1.2 قاعدة تنفيذ كل اختبار

لكل حالة:

1. اكتب المستخدم والفرع والتاريخ قبل البدء.
2. نفّذ الخطوات بالترتيب، ولا تصلح البيانات أثناء الاختبار إلا إذا كانت الخطوة نفسها تتطلب ذلك.
3. سجّل رقم الطلب/القيد/الحركة الناتج.
4. راجع النتيجة من شاشة ثانية أو تقرير أو سجل التدقيق، وليس من نفس الشاشة فقط.
5. حدّث الصفحة ثم أعد فتح السجل للتأكد من persistence.
6. إذا فشلت الحالة، انسخ رسالة الخطأ وسجّلها قبل تجربة workaround.

## 2. بوابة الاختبار التقنية

- [ ] `npm run lint` ينجح بدون errors.
- [ ] `npm run typecheck` ينجح بدون TypeScript errors.
- [ ] `npm run test:unit -- --run` ينجح.
- [ ] `npm run test:integration -- --run` ينجح أو تُسجّل الاختبارات المتوقفة وسببها.
- [ ] `npm run build` ينجح، ونسخة production تفتح.
- [ ] لا توجد أخطاء حرجة في Console أو Network أثناء smoke test.
- [ ] API health/status يعمل، وطلبات 401/403/404/422/500 ترجع رسائل منظمة.
- [ ] backup وrestore تجريبيان يعملان، ولا يوجد تسريب secrets في logs أو frontend bundle.
- [ ] تشغيل السيرفر مرتين أو إعادة الاتصال لا ينشئ duplicate jobs أو duplicate orders.

## 3. الدخول، الجلسات، الأدوار والفروع — AUTH

- [ ] دخول صحيح بالبريد وكلمة المرور يفتح الصفحة الافتراضية المناسبة للدور.
- [ ] كلمة مرور خاطئة تُرفض برسالة عامة لا تكشف هل البريد موجود.
- [ ] تكرار محاولات الدخول الفاشلة يفعّل الحماية المتوقعة، ثم يسمح بالدخول بعد انتهاء المدة.
- [ ] دخول PIN — إن كان مفعّلًا — يفتح بصلاحيات الموظف فقط.
- [ ] تسجيل الخروج ثم refresh لا يعيد الجلسة.
- [ ] انتهاء token يعرض رسالة واضحة ويعيد إلى `/login`.
- [ ] فتح route محمي بدون تسجيل دخول يعيد إلى login، ثم يعيد المستخدم للـ route المطلوب بعد الدخول.
- [ ] فتح route غير مسموح به بحساب محدود لا يعرض بيانات ولا endpoint محمي في Network.
- [ ] تبديل الفرع يغيّر البيانات والطلبات والمخزون والتقارير في كل الشاشات.
- [ ] محاولة تمرير `branchId` لفرع آخر عبر URL أو Network تُرفض.
- [ ] تعديل دور أو permission ينعكس بعد إعادة الدخول وبحسب سياسة النظام.
- [ ] حذف/تعطيل مستخدم يمنع الدخول ويُنهي الجلسات حسب السياسة.
- [ ] maker-checker: منشئ العملية لا يستطيع اعتمادها إذا كان غير مخول.
- [ ] Super Admin يستطيع اعتماد الحالات المسموح له بها، ويظهر اسمه في السجل.
- [ ] kick/session notices تظهر على الجهاز الآخر ولا تكسر التطبيق.
- [ ] `/setup` بعد اكتمال الإعداد لا يعرض معالجًا يعيد تهيئة أو يمسح البيانات.
- [ ] رابط تتبع طلب عام يعمل بالتوقيع الصحيح فقط، والرابط المعدّل أو غير الموقّع لا يكشف بيانات.

## 4. لوحة القيادة والنظام العام — DASH

- [ ] فتح `/` يعرض KPIs والرسوم والطلبات والتنبيهات بدون crash.
- [ ] فلاتر التاريخ والفرع تغير الأرقام والرسوم فعليًا.
- [ ] أرقام الإيراد، الطلبات، الملغي، المرتجع، المصروف، والربح تطابق مصدرها.
- [ ] أحدث الطلبات تفتح الطلب الصحيح.
- [ ] تنبيه business date يظهر عند وجود تاريخ تشغيل قديم، ويختفي بعد المعالجة.
- [ ] تبديل الثيمات والوضع الليلي يحافظ على قراءة النصوص والـ contrast.
- [ ] إيقاف animations يوقف الحركة دون تعطيل الأزرار أو التفاعل.
- [ ] التحديث الدوري لا يكرر الطلبات ولا يضاعف الأحداث.
- [ ] Ctrl+K يفتح البحث، يعثر على الصفحات، وينقل للمسار الصحيح.
- [ ] الإشعارات تُقرأ وتُعلّم كمقروءة وتظهر تفاصيل الحدث الصحيح.
- [ ] RTL/LTR: لا يوجد overflow أو نص مقطوع في العربي والإنجليزي.
- [ ] Refresh على كل صفحة يحافظ على البيانات المحفوظة ولا يكرر mutation.

## 5. POS، الطاولات، الطلبات والمدفوعات — POS

### 5.1 إنشاء وتعديل الطلب

- [ ] طلب Dine-in بطاولة: إضافة أصناف، modifiers، ملاحظات، كمية، وحذف صنف.
- [ ] طلب Takeaway.
- [ ] طلب Delivery مع عميل وعنوان ومنطقة ورسوم توصيل.
- [ ] Hold ثم Recall للطلب بنفس البنود والأسعار.
- [ ] تعديل طلب مفتوح بعد الإرسال للمطبخ.
- [ ] تقسيم الطلب حسب الأصناف وحسب القيمة.
- [ ] دمج طلبين مسموحين ونقل الطلب بين الطاولات.
- [ ] تطبيق خصم نسبة ومبلغ، مع حدود الصلاحية والحد الأقصى.
- [ ] ضريبة صحيحة بعد الخصم، وتقريب decimal صحيح.
- [ ] منع كمية سالبة، سعر غير صالح، صنف غير متاح، وطلب بلا بنود.
- [ ] double-click أو double-submit لا ينشئ طلبين.
- [ ] order number فريد ومتسلسل حسب سياسة الفرع/اليوم.

### 5.2 الدفع والإيصال

- [ ] دفع نقدي مع حساب الباقي.
- [ ] دفع بطاقة/شبكة.
- [ ] دفع مقسم بين وسيلتين.
- [ ] دفع فاشل: الطلب لا يتحول إلى مدفوع ولا يخصم المخزون.
- [ ] إعادة المحاولة بعد timeout لا تنشئ قبضًا مزدوجًا.
- [ ] الإيصال المعروض يساوي الطلب في البنود والخصم والضريبة والإجمالي.
- [ ] طباعة 80mm وA4 أو fallback واضح عند فشل الطابعة.
- [ ] فتح/إغلاق درج الكاشير وجرد البداية والنهاية.
- [ ] فرق العهدة يطلب سببًا أو اعتمادًا حسب السياسة.

### 5.3 دورة الحالة

- [ ] New → Preparing → Ready → Picked up/Delivered → Completed.
- [ ] إلغاء قبل الدفع وبعد الدفع مع السبب والصلاحية.
- [ ] void لطلب مسلم أو يوم مغلق لا يتم إلا بالـ force approval المسموح.
- [ ] حالة قديمة أو انتقال متعارض يُرفض ولا يفسد الحالة الحالية.
- [ ] كل تغيير حالة يظهر في audit log مع المستخدم والوقت والقيم السابقة واللاحقة.
- [ ] البيع يخصم المكونات من الوصفة مرة واحدة فقط.
- [ ] البيع يظهر في KDS وOrders Center وReports وFinance.

## 6. KDS، الاستلام، الكشك والصالة — OPS

- [ ] طلب POS يظهر في KDS لحظيًا بدون refresh.
- [ ] فلترة KDS حسب station/priority/order type.
- [ ] New → Preparing → Ready مع منع الانتقالات غير المسموحة.
- [ ] ألوان الأولوية والصوت والشاشة الكاملة تعمل، وإيقاف الصوت لا يمنع تحديث الحالة.
- [ ] انقطاع Socket أو الشبكة ثم عودتها لا يفقد التذكرة ولا يكررها.
- [ ] شاشة `/pickup` تعرض الجاهز فقط.
- [ ] تسليم الطلب يطلب التحقق/التوقيع/الملاحظة حسب الإعداد.
- [ ] التسليم ينعكس في الطلب وفي driver/dispatch عند التوصيل.
- [ ] `/kiosk`: تصفح، تصنيف، modifiers، سلة، idle timeout، إلغاء، دفع، إيصال.
- [ ] انتهاء جلسة الكشك يمسح بيانات العميل السابق.
- [ ] floor designer: إنشاء/تحريك/تغيير حجم/حالة الطاولة ثم refresh.
- [ ] فتح طاولة، نقلها، دمجها، حجزها، وإغلاق الحساب.
- [ ] منع حجزين متعارضين للطاولة نفسها.
- [ ] عدادات الإشغال والطلبات تتطابق مع الطلبات الفعلية.

## 7. الكول سنتر، العملاء، المناطق والشكاوى — CRM

- [ ] إنشاء عميل جديد ومنع duplicate أو التعامل معه حسب سياسة الهاتف.
- [ ] البحث بالاسم والهاتف والعنوان.
- [ ] تعديل بيانات العميل وحفظها بعد refresh.
- [ ] تسجيل طلب بعنوان يدوي، GPS، وpin على الخريطة.
- [ ] حساب رسوم التوصيل حسب المنطقة، مع اختبار حدود المنطقة وخارجها.
- [ ] تعديل/إلغاء طلب أنشأه موظف آخر — مسموح للمشرف فقط.
- [ ] Call Center manager يعرض المكالمات والمشغلين والفاشلة والإحصاءات الفعلية.
- [ ] شكوى: Open → In progress → Resolved/Closed مع ملاحظات وتواريخ.
- [ ] CRM يعرض الطلبات، النقاط، المرتجعات، والرصيد الصحيح للعميل.
- [ ] عرض ETA وfallback للخريطة عند غياب token بدون تسريب مفتاح.
- [ ] رفض عنوان ناقص أو رقم هاتف غير صالح برسالة مفهومة.

## 8. المنيو، الوصفات، الأسعار والطباعة — MENU

- [ ] إضافة/تعديل/نسخ/أرشفة/استرجاع/حذف صنف مع تأكيد.
- [ ] إنشاء فئة، ترتيبها، إخفاؤها، وإظهارها في POS.
- [ ] سعر أساسي، سعر فرع، سعر منصة، وعروض/markup.
- [ ] modifiers والخيارات الإجبارية والاختيارية وحدود الكمية.
- [ ] صورة صنف: رفع، ضغط، حذف، وfallback عند عدم وجود صورة.
- [ ] وصفة: إضافة مكونات، وحدات، yield، تكلفة، وتحديث التكلفة عند تغير سعر المكون.
- [ ] بيع صنف بوصفة يخصم المكونات الصحيحة، ولا يخصم الصنف مرتين.
- [ ] صنف ناقص المكونات يتصرف حسب السياسة: منع/تحذير/بيع.
- [ ] استيراد وتصدير CSV: أعمدة ناقصة، duplicate، أرقام غير صحيحة، rollback أو تقرير أخطاء.
- [ ] ربط الصنف بطابعة المطبخ/البار/التعبئة.
- [ ] تعديل receipt template ثم طباعة ومراجعة العربي والضريبة واللوجو.
- [ ] الأسعار والضرائب تظل ثابتة على طلب قديم بعد تغيير الإعدادات.

## 9. المخزون والموردون والمشتريات — INV

- [ ] إنشاء صنف مخزني ووحدته وحد إعادة الطلب والحد الأدنى.
- [ ] بحث/فرز/فلتر وbulk update مع preview وtoast صحيح.
- [ ] إضافة مورد وتعديله وتعليقه، مع منع الحذف عند وجود حركات.
- [ ] إنشاء PO، حفظ مسودة، إرسال، اعتماد، طباعة، وإلغاء.
- [ ] استلام كامل، استلام جزئي، واستلام زائد/ناقص.
- [ ] استلام يضيف الكمية للمخزن الصحيح وبالتكلفة الفعلية والـ batch/expiry إن مفعّل.
- [ ] فاتورة المورد: رقم، ضريبة، خصم، تاريخ استحقاق، إجمالي، اعتماد، وقيد مالي.
- [ ] تحويل بين مخزنين: خصم المصدر، إضافة الوجهة، حركة واحدة مترابطة.
- [ ] طلب مخزني بين فرع والمخزن المركزي: طلب → اعتماد → توريد → استلام.
- [ ] جرد blind count، draft، فروقات، اعتماد، وترحيل.
- [ ] منع جردين متزامنين أو معالجة تعارض واضح.
- [ ] سجل الحركات يعرض المصدر والوجهة والمستخدم والوقت والسبب.
- [ ] هالك: كمية وسبب ومرفق واعتماد، ثم نقص المخزون وظهوره في التقرير.
- [ ] reorder/forecast يعتمد على الاستهلاك الفعلي وليس قيمًا ثابتة.
- [ ] فتح المخزون من فرع آخر لا يكشف بيانات غير مسموحة.

## 13. التوصيل والسائقون والمنصات — DELIVERY

## 18. سيناريوهات End-to-End إلزامية

### E2E-01 بيع داخل المطعم

1. افتح shift وجرد البداية.
2. أنشئ طلب Dine-in لطاولة، أضف صنفًا مركبًا وخصمًا.
3. أرسل للمطبخ، راقب KDS، ثم اجعل الطلب Ready.
4. ادفع نقدًا واطبع الإيصال.
5. تحقق من Orders، المخزون، الخزينة، القيد، التقرير، وaudit log.

### E2E-02 طلب توصيل COD

1. أنشئ/اختر عميلًا وعنوانًا داخل zone.
2. سجّل الطلب وتحقق من رسوم التوصيل.
3. عيّن سائقًا، سجّل pickup/delivery وPOD.
4. سجّل التحصيل وأغلق الطلب.
5. طابق الطلب مع Dispatch وDriver cash وFinance وReports.

### E2E-03 شراء واستلام ثم بيع

1. أنشئ PO لمكون، اعتمده واستلمه جزئيًا.
2. راجع الكمية والتكلفة والـ movement.
3. استخدم المكون في وصفة ثم بع المنتج.
4. تحقق من consumption والتكلفة والربح.

### E2E-04 مرتجع بعد الإقفال

1. نفّذ طلبًا واغلق يومه.
2. اطلب مرتجعًا جزئيًا في اليوم التالي.
3. تحقق من approval، عكس المخزون والقيد، وتصنيف الإيراد في التقارير.
4. جرّب force void بدون صلاحية ثم بصلاحية.

### E2E-05 يوم تشغيل كامل

1. افتح shift، نفّذ بيعًا ومصروفًا وشراءً وتحويلًا وهالكًا.
2. نفّذ جردًا ومطابقة خزينة.
3. شغّل Day Close.
4. جرّب عملية جديدة على اليوم المغلق، ثم جرّب reopen بصلاحية وسبب.

استخدم النموذج التالي لكل فشل، والصق JSON من `uat-manual.html` إن كان الاختبار من الواجهة التفاعلية:

### تصنيف الخطورة

- **Critical:** يمنع البيع أو الدخول أو يسبب فقد/تكرار أموال أو يكشف بيانات.
- **Major:** مسار تشغيلي أساسي لا يعمل، أو الأرقام غير صحيحة، مع workaround صعب.
- **Minor:** مشكلة نص/تنسيق/تجربة مستخدم لا تمنع التشغيل.
