# دليل معالجة الأعطال التشغيلي

هذا الدليل مخصص لمدير النظام أو مسؤول الدعم. نفّذ خطوات القراءة أولًا، ولا تغيّر بيانات مالية أو تعيد تشغيل رسائل دفع قبل تسجيل رقم الطلب و`requestId` والفرع والوقت.

## قاعدة التصعيد

صعّد الحالة فورًا إذا ظهر اختلاف في إجمالي الطلب، أو حالة دفع غير مؤكدة، أو قيد محاسبي مكرر، أو فقد بيانات. لا تستخدم SQL يدويًا لتعديل `orders` أو `payments` أو `journal_entries` في الإنتاج.

## 1. الخدمة لا تستجيب

1. افتح `GET /api/status` من نفس الشبكة.
2. إذا كانت الحالة `outage`، افحص سجل التطبيق وقاعدة البيانات ووسيط الرسائل، بدون عرض الأسرار أو headers للمستخدم.
3. افحص `GET /api/ops/status` بحساب `SUPER_ADMIN` أو `OWNER` لمعرفة p50/p95 والمسارات المتجاوزة للـSLA.
4. تحقّق من قاعدة البيانات والـqueue والـprinting من لوحة Integration Health.

لا تعتبر صفحة `/status` دليلًا على أن الـbackend متاح إذا كانت الواجهة تعمل وحدها؛ يلزم backend وبيئة قاعدة اختبار أو staging.

## 2. جلسة المستخدم انتهت

اطلب تسجيل الدخول من جديد. لا تمدد `expiresAt` يدويًا ولا تعاود استخدام refresh token قديم. إذا تكرر الأمر:

- راجع وقت الخادم وتزامنه.
- راجع سجل revoke/expiry من إدارة الجلسات.
- تأكد أن الجلسة والفرع المعروضين يخصان المستخدم نفسه.

## 3. تعارض أوامر POS أثناء انقطاع الشبكة

في Conflict Center:

- `RETRY`: استخدمه فقط للأخطاء المؤقتة مثل 503 أو timeout.
- `DISCARD`: استخدمه بعد التأكد أن العملية لم تُقبل على الخادم.
- `RESOLVE`: راجع الفرع و`Idempotency-Key` قبل إعادة الإرسال.

لا تكرر الدفع يدويًا قبل فحص حالة الطلب والجلسة. الطابور يرفض اختلاف الفرع أو تغيّر payload لنفس مفتاح idempotency.

## 4. الدفع أو الـwebhook غير محسوم

1. افحص order status وpayment session ومرجع المزود.
2. إذا كانت النتيجة `requires_reconciliation` أو `pending`، لا تعلن الطلب مدفوعًا ولا تنشئ payment جديدًا.
3. أعد معالجة DLQ فقط من المسار المالي المحمي وبعد التأكد من أن الخطأ transient.
4. لا تعيد callback يدويًا من متصفح أو script غير موثق؛ احتفظ بـHMAC والمرجع كما وصلا.

الردود السلبية أو الغامضة من gateway لا تُعتبر نجاحًا. أي refund غير مؤكد يجب أن يبقى قابلًا للمراجعة ولا يتحول إلى `REFUNDED` تلقائيًا.

## 5. الرسائل عالقة في DLQ

اعرض metadata فقط: النوع، الفرع، عدد المحاولات، آخر خطأ، ووقت المحاولة. أصلح السبب أولًا، ثم نفّذ replay واحدًا مع مراقبة النتيجة. لا تعدّل payload الخام أو تعيد تشغيل business error.

## 6. الطباعة أو KDS لا يعملان

- افحص Integration Health وحالة الطابعة/الـlocal bridge.
- تحقق أن الجهاز والفرع متطابقان وأن العنوان مخفي عن المستخدم غير المصرح.
- في offline mode، راجع local print queue وKDS local hub.
- لا تغيّر branch binding من واجهة المتصفح.

بعد عودة الشبكة، راقب dedupe وqueue status قبل إعادة طباعة أو إرسال الطلب للمطبخ.

## 7. اختلاف تقرير أو رقم مالي

سجّل الفترة باستخدام `businessDate` والفرع والقناة. قارن المصدر canonical مع drill-down، واستبعد الحالات الملغاة حسب التقرير. لا تعتمد رقم AI أو forecast كقيد محاسبي؛ يجب أن يظهر مصدره ودرجة الثقة وجودة البيانات.

## 8. النسخ الاحتياطي والاستعادة

استخدم فقط:

```powershell
npm run ops:backup-restore-drill
```

الـdrill المحلي مصمم لقاعدة `RestoFlow_Test` ويستعيد إلى قاعدة disposable. لا تشغله على قاعدة الإنتاج. احتفظ بتقرير `VERIFYONLY` ومدة النسخ والاستعادة وعدد الجداول الحرجة، ثم اختبر restore خارج المضيف في staging قبل اعتماد RPO/RTO.

## 9. معلومات البلاغ المطلوبة

أرفق: الوقت والمنطقة الزمنية، الفرع، دور المستخدم، رقم الطلب/العملية، `requestId`، endpoint، status code، آخر حالة معروفة، وصورة من الرسالة بعد إخفاء الأسماء والأرقام والtokens. لا ترفق payment references أو payloads كاملة أو أسرار البيئة.

## ما لا يثبته هذا الدليل

هذا الدليل لا يُغلق اختبارات server restart، يوم التشغيل الكامل online/offline، pilot الشبكة الضعيفة، اعتماد الأجهزة، أو UAT على مزود دفع حقيقي. هذه عناصر قبول مستقلة في خارطة التنفيذ.
