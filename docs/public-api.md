# RestoFlow Public API v1

The public surface is branch-scoped. Reads and order creation are separated by scopes.

## Authentication

Configure `PUBLIC_API_KEYS_JSON` on the server with SHA-256 hashes, scopes, and allowed branches:

```json
[{"id":"partner-a","keyHash":"<sha256 hex>","scopes":["orders:read"],"branchIds":["branch-1"]}]
```

Keys can be rotated by adding the new hash before removing the old one. Set `revoked: true` or an ISO `expiresAt` to disable a key without exposing the raw secret. Managed keys can additionally use `orders:write`, `orders:quote`, `menu:read`, `webhooks:read` and `webhooks:manage`.

Send the raw key only over HTTPS:

```http
X-RestoFlow-API-Key: <raw key>
```

The server never stores or returns the raw key. Missing configuration disables the surface with `503`.

### OAuth 2.0 client credentials

Managed keys can exchange their `client_id` and one-time-delivered `client_secret` at `POST /api/v1/oauth/token` using `grant_type=client_credentials`. The response is a one-hour Bearer token plus a 30-day refresh token. Refresh tokens are stored as hashes, rotated once per use, and rejected on replay. Requested scopes must be a subset of the scopes granted to the client, and every API request rechecks that the client is still active, so revoking the key invalidates its Bearer tokens immediately.

The endpoint accepts either form fields (`client_id`/`client_secret`) or the standard HTTP Basic client authentication. Refresh with `grant_type=refresh_token` and `refresh_token=<token>` returns a new access/refresh pair. Authorization-code grants remain outside the machine-to-machine scope.

### Managed key lifecycle

Owners and super administrators can manage persistent partner keys through the authenticated internal API:

- `GET /api/public-api/keys` returns metadata only (prefix, scopes, branches, expiry, revocation and last-use timestamps).
- `POST /api/public-api/keys` creates a key. The `secret` is returned once and must be copied by the operator; it cannot be recovered later.
- `POST /api/public-api/keys/:id/rotate` atomically revokes the active key and creates a replacement; the replacement `secret` is returned once.
- `POST /api/public-api/keys/:id/revoke` revokes a key immediately.

The management endpoints require `SUPER_ADMIN`/`OWNER` or the explicit `CFG_MANAGE_PUBLIC_API_KEYS` permission. Supported scopes include `orders:read`, `orders:write`, `orders:quote`, `menu:read`, `sandbox:read`, `webhooks:read` and `webhooks:manage`. Every created key must include at least one allowed branch; use `*` for a deliberately cross-branch integration. The legacy `PUBLIC_API_KEYS_JSON` environment configuration remains supported during migration.

### Sample app

A dependency-free Node 20 example is available in [`examples/public-api-node`](../examples/public-api-node/README.md). It demonstrates OAuth token exchange and branch order reads; Webhook creation is opt-in with an explicit flag.

## Endpoints

- `GET /api/v1/openapi.json` — versioned contract.
- `GET /api/v1/branches/{branchId}/orders` — paginated order summaries with `orders:read` and branch allow-list enforcement.
- `GET /api/v1/branches/{branchId}/orders/{orderId}` — one privacy-safe order projection with items, totals, payment state and tracking URL; requires `orders:read`.
- `GET /api/v1/branches/{branchId}/menu` — published, available menu items with the branch/channel price and no cost or internal platform data; requires `menu:read`.
- `GET /api/v1/branches/{branchId}/hours` — branch operating hours, timezone and current `isOpen` state; requires `menu:read`.
- `GET /api/v1/qr/branches/{branchId}/tables/{tableId}/menu` and `POST .../orders` — capability-token QR flow for dine-in tables. The token is generated by the authenticated table action `GET /api/tables/{tableId}/public-qr`, is bound to exactly one branch/table, and cannot be used as a general API key.
- `POST /api/v1/branches/{branchId}/orders/quote` — authoritative quote for menu item quantities with branch tax/service charge and channel delivery fee; requires `orders:quote`. It does not create an order or charge a payment method.
- `POST /api/v1/branches/{branchId}/orders` — creates an unpaid online order through the canonical pricing, stock, KDS and finance pipeline while enforcing branch operating hours; requires `orders:write` and a unique `Idempotency-Key`. The server ignores client totals/prices/payment fields and returns a safe order reference plus `paymentRequired: true`.
- `POST /api/v1/branches/{branchId}/orders/{orderId}/checkout` — creates or replays a Paymob hosted checkout for an online order; requires `orders:write` and a unique `Idempotency-Key`. The payable amount is read from the saved order, not the request. Checkout URLs are encrypted at rest and the Paymob webhook settles the existing payment session.
- `GET /api/v1/sandbox/orders` — deterministic synthetic orders with `sandbox:read`; never reads production data and returns `X-RestoFlow-API-Sandbox: true`.
- `GET /api/v1/webhooks` — list only subscriptions owned by the current API key (`webhooks:read`).
- `POST /api/v1/webhooks` — create a branch-scoped signed subscription (`webhooks:manage`); the generated signing secret is returned once.
- `DELETE /api/v1/webhooks/{id}` — delete only a subscription owned by the current API key (`webhooks:manage`).
- `GET /api/v1/webhooks/{id}/deliveries` — read sanitized delivery metadata (`webhooks:read`).

Order responses intentionally exclude customer phone/address and payment rows. Use `limit` (max 100) and an ISO `cursor` returned in `paging.nextCursor`.

Authorization-code grants and online card payment capture remain outside this slice. Public order creation is intentionally unpaid until a payment provider flow is completed. Sandbox data is read-only and synthetic. Public webhook payloads remove customer/payment/transport secrets before delivery. Secrets are not returned by list/revoke endpoints, and key creation/rotation/revocation is recorded in the signed audit log without the raw secret.
